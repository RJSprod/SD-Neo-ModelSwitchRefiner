# SD-Neo-ModelSwitchRefiner

A Forge / SD WebUI Neo extension. Four areas share one process and, critically, one GPU:

- **Model chain and refiner** — multi-stage image generation, checkpoint switching, Krea 2 and Flux Klein support (`mc_arch.py`, `mc_plan.py`, `scripts/model_chain*.py`); since handoff 46 MOSS-Image and FIBO 2.0 are recognised from the two class names each one's own extension registers with the host (and MOSS-Image also by Forge Neo's own names, since Forge learned it on 2026-10-21), and the Krea 2 prompt stages stand down for them
- **LLM Studio** — local `llama-server` chat with vision, attachments, roles (`mc_llm_*.py`); since handoff 59 a per-thread **emotion** (Oobabooga's *character bias*: `mc_llm_emotions.py`), since handoff 64 at the end of the thread's system prompt or, by a switch since 65, as the start of the reply, and the background **cache update** after a change of it (`mc_llm_cache_update.py`; docs/07 §40); since handoff 63 **Start reply with**, words of yours the thread's next reply begins with, once (`mc_llm_start_with.py`; docs/07 §41)
- **Voice Chat** — STT and TTS with several selectable engines (`mc_voice_*.py`, `voice/`, `*_worker/`)
- **Voice Box** — VibeVoice 7B or Breeze TTS 2, one at a time, on a card of your choosing: samples (with transcripts), prompts, configurations, pipelines, outputs, voice design (`mc_voice_box*.py` — `mc_voice_box_engines.py` is the registry, `mc_voice_box_fields.py` and `mc_voice_box_render.py` the neutral contract — `mc_voice_vibevoice*.py`, `vibevoice_worker/`, `mc_voice_breeze*.py`, `breeze_worker/`, `mc_turns_guests.py`, `javascript/voice_box.js`)
- **Creative / spatial prompt tooling** — treatments, bounding-box regions, literal prompts (`mc_creative_*.py`, `mc_spatial*.py`, `prompt_master/`)
- **Gallery Quadrant** — the user's own `sd-gallery-quadrant` extension carried in as it was (handoff 45): five tap zones over the gallery's preview, with the top-left zone's destination a setting — the browser's downloads or a folder on this machine, written by a route (`mc_gallery_quadrant.py`, `javascript/model_chain_gallery_quadrant.js`, the stylesheet's *Gallery Quadrant* section)

- **LoRA Details** — the user's own `SD-ForgeNeo-ExtendedLoraDetails` extension carried in (handoff 51): a CSV library of what Civitai says about each LoRA, the fetch that fills it, the gallery images behind the prompts, the folders each UI Preset shows, and Forge's LoRA dialog laid out again the width of the window (`mc_lora_*.py`, `mc_extra_networks_folders*.py`, `mc_extra_networks_filter.py`; docs/26 is the record)

`README.md` is long and acts as the behavioural specification. Treat it as authoritative for declared behaviour and update it when behaviour changes.

The hard problem running through the whole codebase is **VRAM arbitration**: the image model and the language model want the same card, and most of the subtle bugs in this project's history come from that contention. Since handoff 28 there is a third party to it: Mini Paint NEO's WanGP, on a card of its own, which `mc_wangp.py` gives priority over the language model on that card. Since handoff 31 there is a fourth: a GPU speech guest (VibeVoice 7B, for the Voice Box tab, `docs/23-voice-box.md`) that takes a card only through a turn — `mc_turns.py` decides whose turn it is on each card, holds image jobs at a gate while one is next, parks and brings back the image model, and borrows WanGP's card from Mini Paint through a lease. Since handoff 32 the guest exists: `mc_turns_guests.py` registers it, `mc_voice_vibevoice*.py` and `vibevoice_worker/` are the engine, and `mc_voice_box*.py` with `javascript/voice_box.js` are the tab. Since handoff 44 the guest is either of two engines, one at a time (`docs/25-voice-box-engines.md`): Breeze TTS 2 (`mc_voice_breeze*.py`, `breeze_worker/`) beside VibeVoice, each registered as a guest under its own name, and `mc_voice_box_engines.select` ends one engine's workers on every card before the other may start.

## Project history lives in Claude artifacts

Sessions from 2026-08-20 onward each published a detailed handoff as a **private Claude artifact** titled `Handoff NN - <topic>`. They contain turn-by-turn logs, design decisions, rejected alternatives, and gotchas.

**They are not loaded automatically.** To use them:

1. `Artifact` tool, `action: "list"` — the handoffs appear as `Handoff 01` … `Handoff 30`
2. `action: "read"` with the URL of the one you need

**Read the relevant handoff before reopening an area it covers.** The index below tells you which one.

### Coverage limits — read this before assuming

- **Numbering gaps at 06 and 19 are not missing records.** Those sessions targeted other repositories (`SD-ForgeNeo-ExtendedLoraDetails` and `NEO-webui-auto-tls-https`); their handoffs live there.
- **The handoffs do not cover the whole repository.** PRs #1–#44 predate the handoff record entirely; PRs #82–#102 (prompt-box UX, QoL/UX refactor, pipeline header, design-intent spec review) fall between handoffs 14 and 15 with no handoff written; and PRs #192–#223 (the Forge Assistant flyout, rounds one to four: read-aloud, message actions, auto-attach, literal prompt boxes, new thread, system-prompt editor, in-place edit, Send to Generate) fall between handoffs 27 and 28 with no handoff written — handoff 28 names them only in its state section; and PRs #245–#246 (the Forge Assistant's free RAM and VRAM in the header's drag space, and WanGP's Generate beside the ⋯ menu, which never locks) fall between handoffs 38 and 39 with no handoff written. Absence from this index does **not** mean the work never happened — check `git log` before concluding anything is unimplemented.
- **Handoff 01's internal date is wrong.** It states 2026-09-03; the work was 2026-08-20. Later handoffs carry correct dates.
- **Sessions under-report their own PRs.** Several handoffs say "no PR opened" because the *user* opened it from the UI rather than the session. The PR numbers in the index below come from `git log` and are authoritative.

### A thread's emotion steers one of two ways, and each has its own cache rule — a trap

Since handoff 65 a switch (`mc_llm_emotions.mode()`, one choice for every thread, kept with the list; `set_emotion_mode`; *How it steers* at the top of both Emotion pickers) chooses between the two ways below: **System prompt** (`SYSTEM`, the default) and **Starts the reply** (`PREFILL`, Oobabooga's own and handoffs 59 to 63's, brought back by the user's word: "a toggle that allows me to switch between the two ways"). Every place that builds a thread's prompt asks the way (`_emotion_mode`, `_emotion_note(..., steer)`): under `PREFILL` the system prompt is the character's own, the line is a trailing assistant message for a fresh reply only (`_fresh_reply`), followed by an empty line at the user's word (`mc_llm_emotions.opening`, `BREAK` `"\n\n"`, where Oobabooga ends on a space) and then a start of yours with nothing put between, and the reply is read again after it is saved; under `SYSTEM` what follows holds. `Unechoed` and `without` compare what was sent exactly, its ends trimmed and nothing inside it folded: a start of yours keeps its own line breaks, and a folded comparison left such a start's echo in the reply. Since handoff 64 a thread's emotion (`mc_llm_emotions`), under `SYSTEM`, is put at the end of the thread's system prompt in one shape (`system_note`, through `prompt.build`'s `system_extra`), for **every** request in the thread, Continue included; the character's own prompt -- its override or the built one -- is never edited and the editor shows it as it is. ### Forge repeats a batch's prompts up to a common multiple of their lengths — a trap

Forge Neo's commit `49bc706` (2026-10-30, "batching") changed `stack_conds` in `modules/prompt_parser.py`, which stacks every image's conditioning before each sampling step. Prompts of different lengths, which a wildcard picked per image gives a batch, used to be padded to the longest with copies of their last token; now every prompt is repeated whole up to the least common multiple of the lengths, with no limit. Krea 2's conditioning is unpadded and float32 (12 hidden layers × 2560: 120 KiB a token, in system RAM until the sampler moves it onto the card), so two prompts of 250 and 254 tokens became 31,750 tokens each, 7.3 GB for a batch of two, and every wildcard batch above one ran the user's 24 GB card out of memory (handoff 61; the user confirmed that removing the wildcard made the batch work). Forge's own cond/uncond batching (`backend/sampling/condition.py`) and ComfyUI both refuse a repeat past four times the shorter prompt; this one has no limit. `mc_prompt_padding` wraps `stack_conds` and gives a call whose tensors differ only in length the old padding (*Pad a batch's prompts to the longest, as Forge did before October 30*, on). It is tied to the host by a probe at every start, not by a build pin: 3 and 5 tokens, 15 back is the repeat, 5 the padding, anything else leaves Forge's function alone with a warning. A pin would bring the error back at every Forge update; the batch-count override's pin has kept that override off on the user's machine since their first 2.31 start. This failure's shape in `model_chain.log`: a Stage 1 pass that never logs its working VRAM, every model unloaded after it (Forge's console says *Encountered Out of Memory during Sampling; Unloading all Models*), and free system RAM down by tens of GB between tries. Whenever Forge Neo changes how conditioning is batched, read `prompt_parser.py` and `condition.py` against an LLM encoder's unpadded lengths, not CLIP's 77-token chunks; `tests/test_prompt_padding.py` runs Forge's own code from both sides of the change.

**The fix is temporary: retire it once Forge Neo fixes this itself**, at the user's word ("if forge neo fixes this loading, then we can deprecate our fix"). The start of `model_chain.log` tells: *Forge pads a batch's prompts of different lengths itself on this build … the padding can be retired* (the probe answered 5) in place of the repeat line, or a warning that the probe's answer was not recognised, which means Forge rewrote the function and its new code is to be read first. Both assume the engine the host holds is the one it last encoded into, and this extension breaks that whenever it changes the engine without changing the loading parameters: a warm swap from the RAM cache hands back an engine still holding its last generation's pictures (a Stage 1 brought back after a Stage 2 on another checkpoint, into a generation with ImageStitch off, edited pictures no longer in the gallery), and a drop the host reloads from its recipe (Cold LoRA's eviction, a Voice Box turn's *From its recipe*, a cleared stale hash) hands it an empty engine that the memo still matches (the edit ran without its pictures). Since handoff 46 each of those places empties the incoming engine as a load would (`mc_memory._start_without_references`, the lists emptied directly because the engine's own `clear_references` synchronises the device) and drops the memo (`forget_stitch_memo`); a new place that changes the host's engine needs the same. Parking in RAM keeps the very engine, pictures and memo alike.

The user's Forge runs the Lobe theme (`lobehub/sd-webui-lobe-theme`), and it does more than restyle. Its night mode's accent is **white** (black by day), which is why Gradio's primary buttons were solid white blocks there until handoff 43's quieter night mode (`model_chain_quiet_night`, `javascript/model_chain_night.js`, the `data-mc-night` section of `style.css`). ### A Gecko browser pans the page under a touch the page has claimed — a trap

The Forge Assistant's handles say `touch-action: none`, cancel every `touchmove` of a live drag from a non-passive listener on the handle, and take pointer capture — and the user's `model_chain.log` (handoff 43, docs/22 §3.34) showed a Gecko browser (a desktop Firefox 153 UA with zero touch points: LibreWolf on a Windows touchscreen under its fingerprinting defence, or Firefox Android in desktop mode) panning the page by the finger's travel under every drag anyway, with every touchmove still reported cancelable and no `pointercancel` ever sent. ### A swipe past the end of a sideways scroller is the browser's Back — a trap

Chromium's swipe-to-navigate (a finger on a touch screen; a touchpad's two fingers) takes any sideways swipe that no scroller can take — a row of cards already at its first card, swiped right, is one — and decides it from the **page root's** `overscroll-behavior` alone, and only while the scroller under the finger leaves its own at `auto`: a scroller's `contain` or `none` hands the overscroll straight to navigation, the root's `none` notwithstanding, and neither a cancelled first `touchmove` nor `touch-action: pan-right pan-y` at the end stopped it (Chromium 141, fingers driven through the DevTools protocol's `Input.dispatchTouchEvent`; `Input.synthesizeScrollGesture` with touch moves nothing in that headless build, and Playwright's sideways `mouse.wheel` carries no touchpad phases, so neither shows it). ### Forge's extra-network script looks for a page's cards under `#<tab>_extra_tabs` — a trap

### Gradio writes every block's `overflow` inline — a trap

Gradio 4.40's `Block.svelte` writes `overflow: visible` or `hidden` as an **inline style** on every block (`allow_overflow`: visible for an HTML component, hidden for a textbox), beside `min-width` and the border. An inline declaration outranks any stylesheet rule that is not `!important`, so the theme's `overflow: hidden` on Forge's `html_info_*` paragraph — kept in the page one pixel wide under `white-space: nowrap`, for what reads it — never applied on a real page: the paragraph's one line, the whole infotext, overflowed it and widened the page by that much. On a desktop that was a horizontal scrollbar since #272; on a phone (handoff 45's second run) Chromium widens the **layout viewport** — what `fixed` and `sticky` are held against, what `innerWidth` and `innerHeight` report, while `documentElement.clientHeight` stays the window's — to a page wider than the window and lets it be zoomed out to that width, so the one scroller's hold was computed against half the scrollport and the Forge Assistant's fill grew the gallery to the zoomed-out glass. The paragraph clips `!important` now, and Gradio's container is clipped sideways under the theme (`overflow-x: clip !important` on `div.gradio-container.app`, over Forge's `overflow: visible !important`; `clip` makes no scroll container, so sticky still holds against the page; `html { overflow-x: hidden }` holds nothing there, because Chromium takes the minimum scale from the document's layout overflow). The test page's blocks carry Gradio's inline style; a stand-in block without it proves nothing about `overflow` on Forge. Chromium's cascade is one CDP call away (`CSS.getMatchedStylesForNode`), and `Page.getLayoutMetrics` says what the layout viewport is.

### A callback that changes a child list on every after-update is a loop — a trap

Forge's `script.js` observes `<gradio-app>` (`childList`, `subtree`) and runs every extension's `onAfterUiUpdate` callbacks 250 ms after any burst of changes. A callback that adds, removes or replaces a node on every run — the same title written again as a new text node, a menu emptied and refilled, a canvas redrawn from unchanged data — raises the next run itself, and the page updates forever, on every tab, with every extension's callbacks running each time: about 50 ms out of every 300 on the user's machine, which their drag log showed as a stall under every drag of the flyout (handoff 43, docs/22 §3.36). ### Gradio makes the tab buttons again on every change of tab — a trap

Gradio 4.40's `Tabs.svelte` draws the selected tab's button and every other one from two branches of one `{#if t.id === $selected_tab}`, so a change of tab destroys the pressed button and the one that was selected and creates new ones holding only the name -- no class, attribute or child anything put on them survives, and the selected one has no click handler of its own. ### FastAPI resolves a postponed annotation against the handler's module globals — a trap

Under `from __future__ import annotations` a route handler's `request: Request` is the string `"Request"`, and FastAPI evaluates it against the handler's `__globals__` — the module's, never the enclosing function's locals. The Gallery Quadrant's first build imported `Request` inside `install()`: the string resolved to nothing, FastAPI took `request` for a required **query parameter**, and every save from a browser answered **HTTP 422** (`{"loc": ["query", "request"], "msg": "Field required"}`; the user's report from a phone, after #292). The stand-in host has no FastAPI, so every test passed. `Request` and `JSONResponse` are module globals now, guarded (`mc_voice_box_api.py` had always done it that way; `docs/04-progress-eta.md` had named the same trap for `ProgressRequest`), and `tests/test_gallery_quadrant.py` evaluates the handler's hints the way FastAPI does, with a stand-in `fastapi` where the container has none, and runs the route on a real FastAPI app where it has one. Reproduced in a venv with Forge Neo's pins (`fastapi==0.127.1`, `pydantic==2.10.6`) before the fix and green after it. Any route added here under postponed annotations needs its annotation names in the module's globals.

### A fling is the browser's, and CSS scroll snap is not a brake — a trap

Once a finger lifts, Chromium's browser process synthesizes inertial scroll updates from the finger's last movements and the compositor applies them until the curve ends or an update cannot be applied; a page's scroll listener runs after the frame that crossed has been drawn, and a position written back from it is a frame or two late while the fling keeps pushing. The one scroller's **momentum break** (`model_chain_theme.js`, "the momentum break between the two phases"; docs/24 §0) therefore gives the browser an **edge** for the fling's time instead of fighting it: downward, the row's ancestor just inside the scroller is clipped (`max-height`, `overflow-y: clip`, inline and important) so the range ends at the boundary; upward, a fling read crossing is put back and the scrolling element held `overflow: hidden`, which Chromium reads as the fling's end. CSS scroll snap was tried first and does not do this: a snap area larger than the snapport leaves the scroll alone only when the intended position is more than a snapport from the area's aligned edge, so every position within a view of the boundary snapped to it (a third of a view under `proximity`), and `scroll-snap-stop: always` stopped no fling (Chromium 141, flings driven through `Input.dispatchTouchEvent` with timestamps, which this headless build does turn into flings). Four timing traps inside the break, each found by a test: a programmatic scroll's `scrollend` arrives a frame later and can land after the next `touchend`, so a `scrollend` counts as the fling's end only once the fling has scrolled; the scroll back to the boundary has a `scrollend` of its own, so the hold is let go on quiet alone; a fling can land on the boundary **exactly** in one frame, so a crossing is "at or past the boundary a frame ago, below it now", never "above, then below" (that condition passed twice and then failed four runs of six); and quiet is counted in **animation frames**, not on the clock, because under four workers the starved main thread dispatched the fling's scroll events after a quarter-second timer had already let the break go -- a frame's scroll events run before its animation callbacks, so a frame count cannot get ahead of them. The Forge Assistant's fill lays the results column out again on any page change and reads the sticky bar 8 px higher once the page is scrolled past its padding, so Generate can sit 8 px higher inside the held column after a re-fit while scrolled: the fill's, not the break's, and not new.

## Standing conventions

These recur across the handoffs and the user has restated them repeatedly.

- **Develop on the designated branch.** Commit with clear messages, push when complete. Since handoff 34 the repository's default branch is **`main`** (made at `d34d21d` when 33 was rolled back); the user's WebUI extension folder follows it, and pull requests go into it.
- **Do not open a pull request unless explicitly asked.** The user opens them from the Claude Code UI.
- **No model identifier** in commit messages, PR text, code comments, or anything else pushed to the repository.
- **Run the full suite before every push**: `python3 tools/run_tests.py`, not just the file you touched. It runs every test on every core through pytest-xdist, which `.claude/hooks/session-start.sh` installs in web sessions (about 2½ minutes on four cores, 7¼ on one; `--serial` for file order). Ordering-dependent failures exist: a test passing alone may fail in the suite, or beside another worker. While working, `python3 tools/run_tests.py --affected` runs only the test files the change can reach (`--list` says why): it follows imports, files named in strings, listed folders and the conftest fixtures a test asks for, and cannot see state one test leaves for another, so it never stands in for the full run. `tests/test_vibevoice_upstream.py` skips here: it runs the VibeVoice worker against upstream's own code (a tiny model on the CPU) and needs `torch`, `transformers` 4.51.3, `diffusers` and the `vibevoice` 0.0.1 wheel in a venv; run it with that venv's pytest (about a minute) whenever the worker's solver, attention or per-take randomness changes. `tests/test_llm_studio_live.py` skips too unless `MC_GRADIO_PYTHON` names a venv with Gradio 4.40.0, Playwright and Mini Paint NEO's pins (see the Gradio trap above); run it whenever LLM Studio's action row, its marker or its tap handling changes — the node harness alone passed a build on which no tap worked. A fresh web container lacks `httpx`, without which 135 LLM tests error at import (`prompt_master`'s downloader), and the Playwright package, without which every real-browser test skips; `.claude/hooks/session-start.sh` installs both since handoff 43, and the tests' launcher finds the container's own Chromium when Playwright's does not match it.
- **A test never writes into the checkout.** The stand-in host's data path is `.`, so a voice, LLM or LoRA path a test forgot to redirect lands in `model_chain_voice/`, `model_chain_llm/` or `model_chain_lora/` of the repository, where every later test, run and parallel worker finds it. A guard in `tests/conftest.py` fails such a test: ask for `voice_root` or `lora_root`, or point `mc_llm_paths.data_root` at `tmp_path`.
- **Mutation-check new tests.** A test asserting a new invariant must fail when the change is reverted. Several tests in this project's history passed for the wrong reason until checked this way. A mutation that puts a Python file back within the same second at the same size (a `2` for a `3`) leaves a `.pyc` compiled from the mutant that Python takes for current — the file says one thing and the imported module another, and the full suite then fails a test that passes on the file as written. Delete the module's `__pycache__` entry after every restore (handoff 43's mutation tools do).
- **When a behaviour change invalidates a test's setup** (not its intent), translate the setup rather than deleting the test.
- **Do not edit files while pytest is running** — it invalidates the run.
- **Update `README.md`** when declared behaviour changes.
- **No path on this machine, no file of the user's and no text of the user's in any log line.** The user's rule since handoff 47, for `model_chain.log` and the console alike: never an absolute path (the install, a data directory, the log file's own folder), never the name of a file or folder the user made or chose (an output, a render, a sample, an attachment, a conversation, a save's destination), never a prompt or a message. Models and LoRAs are named as the host names them, because a log that cannot say which model was loaded explains nothing; presets, profiles, layouts and characters are named, being choices from a list; counts, sizes and durations are the rest. Two layers hold it: the lines themselves (every logger call was read in handoff 47 and the ones carrying a path or a user's file rewritten; `tests/test_log_privacy.py` holds the old wordings as absent), and `mc_log_privacy.NoPaths`, a filter `mc_memory._make_logger` puts on the `model_chain` logger that every module logs through, which replaces any absolute path that reaches a record anyway, tracebacks included, with `<path>`. A new line that needs a location says which folder in words (*the logs folder of the LLM data directory*), never the path; a line that would name the user's file says what happened without it; a module logs through `logging.getLogger("model_chain")` and no other name, which the same test holds.
