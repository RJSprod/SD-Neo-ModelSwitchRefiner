# SD-Neo-ModelSwitchRefiner

A Forge / SD WebUI Neo extension. Four areas share one process and, critically, one GPU:

- **Model chain and refiner** — multi-stage image generation, checkpoint switching, Krea 2 and Flux Klein support (`mc_arch.py`, `mc_plan.py`, `scripts/model_chain*.py`); since handoff 46 MOSS-Image is recognised from the two class names its own extension registers with the host, and the Krea 2 prompt stages stand down for it
- **LLM Studio** — local `llama-server` chat with vision, attachments, roles (`mc_llm_*.py`)
- **Voice Chat** — STT and TTS with several selectable engines (`mc_voice_*.py`, `voice/`, `*_worker/`)
- **Voice Box** — VibeVoice 7B or Breeze TTS 2, one at a time, on a card of your choosing: samples (with transcripts), prompts, configurations, pipelines, outputs, voice design (`mc_voice_box*.py` — `mc_voice_box_engines.py` is the registry, `mc_voice_box_fields.py` and `mc_voice_box_render.py` the neutral contract — `mc_voice_vibevoice*.py`, `vibevoice_worker/`, `mc_voice_breeze*.py`, `breeze_worker/`, `mc_turns_guests.py`, `javascript/voice_box.js`)
- **Creative / spatial prompt tooling** — treatments, bounding-box regions, literal prompts (`mc_creative_*.py`, `mc_spatial*.py`, `prompt_master/`)

`README.md` is long and acts as the behavioural specification. Treat it as authoritative for declared behaviour and update it when behaviour changes.

The hard problem running through the whole codebase is **VRAM arbitration**: the image model and the language model want the same card, and most of the subtle bugs in this project's history come from that contention. Since handoff 28 there is a third party to it: Mini Paint NEO's WanGP, on a card of its own, which `mc_wangp.py` gives priority over the language model on that card. Since handoff 31 there is a fourth: a GPU speech guest (VibeVoice 7B, for the Voice Box tab, `docs/23-voice-box.md`) that takes a card only through a turn — `mc_turns.py` decides whose turn it is on each card, holds image jobs at a gate while one is next, parks and brings back the image model, and borrows WanGP's card from Mini Paint through a lease. Since handoff 32 the guest exists: `mc_turns_guests.py` registers it, `mc_voice_vibevoice*.py` and `vibevoice_worker/` are the engine, and `mc_voice_box*.py` with `javascript/voice_box.js` are the tab. Since handoff 44 the guest is either of two engines, one at a time (`docs/25-voice-box-engines.md`): Breeze TTS 2 (`mc_voice_breeze*.py`, `breeze_worker/`) beside VibeVoice, each registered as a guest under its own name, and `mc_voice_box_engines.select` ends one engine's workers on every card before the other may start.

### Shared with Mini Paint NEO — do not rename

The class `forge-assistant-focus-root` (put on the focused panel by `forge_assistant_focus.js`) is read by Mini Paint NEO's `style.css` and `browser/minipaint_wangp.js` to make its WanGP tab the frame alone under focus mode. Renaming it here breaks that silently. The other shared things are older: the dialog layer `--minipaint-dialog-layer: 2000`, the `minipaint:overlay` event, and `visible()`'s reading of a `visibility: hidden` panel as not showing (a parked WanGP panel). And one newer, since handoff 31: **the card lease**, `minipaint_neo.wangp.turns` (`request`/`state`/`flush`/`release`/`report`, a record of exactly `LEASE_KEYS`), which `mc_wangp.lease_*` calls and `mc_turns` drives. Its key set is held closed on both sides (`mc_wangp.LEASE_KEYS` reads a record missing a key as no answer), its `flush` is asynchronous (measure after `held`, never after `flush` returns), and a lease that is `holding` with `bridge_hold: unsupported` is refused rather than waited on. Mini Paint's `docs/wangp/CONTRACTS.md` is its other half.

Since 2026-10-02 there is one more: **`minipaintWanGP.generate()`**, which the flyout's ▶ on the WanGP tab (`tab_wangp`) calls — WanGP's own Generate for the live page, nothing overridden, queued when WanGP is busy. Its name and its answer's `ok`, `status` and `message` are read here; Mini Paint's protocol test holds that it overrides nothing. It stays outside Mini Paint's Clipboard readiness gate on purpose: the user wants ▶ to press WanGP's Generate on whatever model the page is on.

And one in the other direction, read *there*: **the external LLM API, `mc_llm_api`** (`docs/21-external-llm-api.md`), which Mini Paint's `clipboard/enhance.py` imports from this extension's folder. Its MiniMax H3 presses call `submit_minimax`; since 2026-10-03 its LTX 2.3 Distilled presses call `submit_ltx` (`mc_llm_ltx.py`: the first frame only, shown to the model, written into Prompt Studio's history as a *[No settings]* entry) once `capabilities()["kinds"]` lists `"ltx"`, and its enhancement view shows `system_prompt("ltx23", has_image)` as the default it overrides. Since 2026-10-04 its LTX 2.5 Distilled presses call `submit_ltx(..., model="ltx25")` once `capabilities()["ltx_models"]` lists `"ltx25"`: the same writer under the same instructions, one system prompt for both at the user's request, with `model` only naming the prompt (the status line, the console, the Prompt Studio entry's `written_for`); its view edits one LTX set for both, and `system_prompts()["ltx25"]` says `same_as: "ltx23"`. Renaming `submit_ltx` or the `kinds` value makes Mini Paint refuse every LTX press with `ENHANCE_LTX_UNSUPPORTED`; renaming the `ltx23` variant leaves its view with no default to show; renaming `ltx25` or `ltx_models` still writes an LTX 2.5 prompt in the right words but names it LTX 2.3, because Mini Paint asks without `model` when the list does not name it (an unknown model is refused, `unknown_model`).

### Not superseded — a trap in the other direction

**The Voice Box's two engines coexist.** VibeVoice 7B (31–38) and Breeze TTS 2 (44) are both live, chosen one at a time in the Voice Box (`mc_voice_box_engines.SPECS`). Breeze did not replace VibeVoice: do not "clean up" either, and do not make `mc_voice_box.py` name an engine again — it holds no `vibevoice` (a test holds that), and VibeVoice's flat configuration keys are the registry's `DEFAULT_ENGINE` and the adapter's `FLAT`, kept for older pages and records. Breeze's *Flash attention 2* runs its text encoder only: its decoders hand transformers 4.57 a 4-D mask that its Flash path reads as padding, so they run eager under that choice — do not "fix" the worker to load the whole model with Flash attention 2. And its fast path graphs the text encoder **only under SDPA**: upstream's `TextEncoderGraphCache` sets the encoder to SDPA when it is built, whatever was chosen, so a graph under Flash attention 2 or Eager would run SDPA while the output's infotext named the choice (found by a review against upstream's code; `test_the_fast_path_graphs_the_text_encoder_only_under_sdpa`). And where Triton is missing — Windows — the fast path still captures the depth decoder's and the codec's CUDA graphs, **uncompiled** (`Upstream.graphs_without_compile`): upstream ties each of those graphs to `torch.compile`, and the first build, which turned both stages off with the compiler, ran the owner's first render on an RTX 5090 at 424 ms a frame, five times slower than real time. Do not tie `fast_depth_decoder` or `fast_codec` back to `compile_available()`; upstream's own batch path captures the depth decoder uncompiled (`breeze_infer/batch.py`).

**The three TTS engines coexist.** Kokoro (17, 18), Sopro V2 (22) and PocketTTS (23, 24; 3.3.0 since 42) are all live, selectable backends registered in `mc_voice_engines.py` via the `ENGINES` tuple. Later engines did **not** replace earlier ones. Do not "clean up" Sopro or Kokoro as dead code. LavaSR (24, 26) is the Voice Pipeline's bandwidth-restoration stage (it rebuilds the top of the spectrum a small TTS model cannot generate, after DPDFNet), not a fourth TTS engine. VibeVoice (31, 32) is not a fourth Voice Chat engine either: it is a GPU guest for the Voice Box tab (phase 3, a Voice Chat engine, was built in 33 and rolled back at the user's request — see the superseded table), and every Voice Chat engine stays CPU-only.

### Recognising an architecture arms the Krea 2 guard against it — a trap in the other direction

The Krea 2 checkpoint guard (`mc_creative_krea.checkpoint_objection`, owned by `mc_krea_pipeline.objection`) lets a checkpoint nobody can identify through on purpose and refuses every *recognised* architecture that is not Krea 2, in Creative Mode, Spatial Layout and the plan. So a row added to `mc_arch.py`'s table is not only geometry and a CFG default: it makes the guard refuse that model by name, which is what the user asked for MOSS-Image (handoff 46) and what will happen to the next model added. Neutralize Prompt is deliberately outside the guard — its answer is plain text — and the guard is asked by the hook before the plan is published and before anything runs, whether or not Creative Mode is on; a Creative-on generation left to the roll's own check had Spatial composing Krea's layout for the refused checkpoint.

### The host's theme rewrites the page — a trap

The user's Forge runs the Lobe theme (`lobehub/sd-webui-lobe-theme`), and it does more than restyle. Its **SVG icon** option, on by default, runs once when its app mounts (and again when its prompt editor does) and replaces the *whole content* of every `<span>` whose text contains `×`, `⤡`, `⊞` or `🖫` with a 36 px icon, and of every `<button>` whose text holds one of its emoji with a 16 px one. A span with a `×` anywhere inside it goes whole: the Voice Box's status actions lost Cancel, Clear queue and Unload that way, leaving one large X beside *Ready* (handoff 36). Never write `×` as text inside a span; draw it. ### A Gecko browser pans the page under a touch the page has claimed — a trap

The Forge Assistant's handles say `touch-action: none`, cancel every `touchmove` of a live drag from a non-passive listener on the handle, and take pointer capture — and the user's `model_chain.log` (handoff 43, docs/22 §3.34) showed a Gecko browser (a desktop Firefox 153 UA with zero touch points: LibreWolf on a Windows touchscreen under its fingerprinting defence, or Firefox Android in desktop mode) panning the page by the finger's travel under every drag anyway, with every touchmove still reported cancelable and no `pointercancel` ever sent. Gecko's compositor decides a touch on its own once the page has not answered within its content-response window, and a busy Gradio page answers late; nothing said afterwards in a listener reaches that decision. The only thing that holds is to make the page unscrollable for the drag's duration (`lockScroll`: inline `overflow: hidden` with `scrollbar-gutter: stable` on the scrolling element and the focus root). Chromium honours all three of the page's words, so every Chromium test passed against a build that failed on the user's machine twice; a touch behaviour proved in Chromium is proved for Chromium.

### A swipe past the end of a sideways scroller is the browser's Back — a trap

Chromium's swipe-to-navigate (a finger on a touch screen; a touchpad's two fingers) takes any sideways swipe that no scroller can take — a row of cards already at its first card, swiped right, is one — and decides it from the **page root's** `overscroll-behavior` alone, and only while the scroller under the finger leaves its own at `auto`: a scroller's `contain` or `none` hands the overscroll straight to navigation, the root's `none` notwithstanding, and neither a cancelled first `touchmove` nor `touch-action: pan-right pan-y` at the end stopped it (Chromium 141, fingers driven through the DevTools protocol's `Input.dispatchTouchEvent`; `Input.synthesizeScrollGesture` with touch moves nothing in that headless build, and Playwright's sideways `mouse.wheel` carries no touchpad phases, so neither shows it). The Voice Box's card row (handoff 44's two-to-the-view layout) therefore has no overscroll-behavior of its own, and while the tab is on screen its script holds `document.documentElement`'s `overscroll-behavior-x` at `none` inline, giving back what the root held when the tab leaves the screen (`holdHistorySwipe`). Anything else here that scrolls sideways under a finger meets the same thing.

### `gradioApp().querySelector` never leaves `<gradio-app>` — a trap

Forge's `gradioApp()` returns the `<gradio-app>` element (its `getElementById` is patched through to the document, its `querySelector` is not), and Forge's own scripts find things through it: `extraNetworks.js` looks up a page's cards, search box and controls by id that way on every sort, search and card press. So does the Model Chain theme's `query()`. The theme's first drawers were appended to `document.body`, outside that element: the quick settings row moved into one was out of the theme's own reach on the next update, which then put it back, found it again, took it again — the row showed and hid at the top of the user's page on every update (the first thing they reported from their machine) — and the extra-network pages in the other were out of Forge's. Anything this extension moves must stay inside `<gradio-app>` (`mount()` in `model_chain_theme.js`), and a test that applies an **odd** number of times is the one that catches a to-and-fro: `test_applying_again_moves_nothing_twice` passed through the whole defect because two applies put the row back where one had.

### Forge's extra-network script looks for a page's cards under `#<tab>_extra_tabs` — a trap

Forge Neo's `javascript/extraNetworks.js` wires a page's live search as `#<tab>_extra_tabs div.card` (its `applyFilter`) and shows a page's controls as `#<tab>_extra_tabs .extra-networks-controls-div > div`, through `gradioApp().querySelector`. The Model Chain theme's first drawer moved the pages into an aside of its own outside that element: every card press and sort still worked (those go by the page's own id), and the search box filtered nothing from then on — the user's report, two rounds later. Anything that redraws those pages has to leave them where Forge's tabs element holds them: the drawer's head is one more child of `#<tab>_extra_tabs`, the pages are drawn in place by the stylesheet, and `tests/test_theme_layout.py` carries Forge's own filter (`FORGE_WIRES`) and types into the drawer's search box. A test that moves a card and finds it by id proves nothing about a selector scoped to its old parent. **Document order matters too**: Forge renders each page twice (empty at UI build, whole at `interface.load`) and wires the first render's controls into its strip, so every page keeps a hidden second copy of its controls under the same ids, and Forge's sort reads the pressed sort button with `gradioApp().querySelector`, the first match in the document. The drawer's head, holding the wired strip, was appended after the pages, so every sort button did nothing (the user's report, three rounds on); the head goes right after Forge's tab strip (`placeHead`), and the test page carries the hidden copy and Forge's sort. A stand-in with each id once proves nothing about a page that has them twice.

### Forge's own mobile script moves Generate — a trap

`extensions-builtin/mobile/javascript/mobile.js` (Forge Neo, not an extension anyone installed) listens for every window `resize`, takes a results column laid out at `offsetLeft === 0` for a phone's stacked layout, and when that answer changes moves `#txt2img_generate_box` — into `#txt2img_results` for a phone, back into `#txt2img_actions_column` for a desktop — regardless of where a theme had put it (Lobe's split previewer keeps it in the gallery's container). Anything that puts the results column on the row's left edge on a desktop reads as a phone to it, and the browser's full screen, which comes and goes with focus mode, is a resize. The docked row did exactly that, and the fix is a pixel of margin on the column while it is docked beside the settings (`forge-assistant-docked-beside`, docs/22 §3.29). Found by a temporary DOM watcher on the user's page after a real Gradio 4.40 page with Lobe's own bundle did not reproduce it in Chromium; the watcher is gone, the test page carries the script.

### A callback that changes a child list on every after-update is a loop — a trap

Forge's `script.js` observes `<gradio-app>` (`childList`, `subtree`) and runs every extension's `onAfterUiUpdate` callbacks 250 ms after any burst of changes. A callback that adds, removes or replaces a node on every run — the same title written again as a new text node, a menu emptied and refilled, a canvas redrawn from unchanged data — raises the next run itself, and the page updates forever, on every tab, with every extension's callbacks running each time: about 50 ms out of every 300 on the user's machine, which their drag log showed as a stall under every drag of the flyout (handoff 43, docs/22 §3.36). The theme's header (`installHeader`, `fit`) and the Krea spatial compact canvas (`compactLoad`) both did it, each found only by counting an idle page's mutation records in Chromium; attribute writes do not reach Forge's observer but wake any other. Write only what changed (`show`, `setClass`, `menuFor`; `drawnFrom`, `drawnInto`), and when adding an after-update callback, run it twice on a settled page under a `childList` observer and expect nothing — `tests/test_theme_layout.py` and `tests/test_krea_spatial_js.py` do. On the user's machine the Forge Assistant's quiet-page watch (`watchChurn`) writes one `Forge Assistant churn` line to `model_chain.log` naming what kept changing when the page updates twenty times in ten idle seconds: the first thing to look for when a drag stutters.

### Gradio's chat bubble is a button — a trap

Gradio 4.40 draws every Chatbot message as `div.message-row > div.flex-wrap > div.message > button[data-testid="bot"|"user"]`: the words are inside the **button**, its select target, which also turns Enter into a click. The first build of LLM Studio's action row (42) took that button for the bubble and refused every tap "inside a button", so on the user's page a tap did nothing, while every node test passed against a stand-in `div[data-testid]`. The script maps a matched button to its `.message` wrapper (`bubbleOf`), appends the row beside the button (never inside it), reads a press inside the host's own button as a press on the message (`messageButtonOf`), leaves Enter to the click it becomes and gives the wrapper no tabindex. The node harness in `tests/test_llm_studio_js.py` draws bubbles in Gradio's shape too (`shape="gradio"`, and a bare `button`), and **`tests/test_llm_studio_live.py` runs the real script on a real Gradio 4.40.0 page in Chromium** (`tests/live/llm_studio_row_live.py`) when `MC_GRADIO_PYTHON` names a venv with Gradio 4.40.0, Playwright and Mini Paint NEO's `tests/requirements.txt` pins (stock 4.40.0 launches only with `fastapi==0.112.2`, `pydantic==2.8.2`, `huggingface_hub==0.24.6`, `gradio-client==1.2.0`); it skips otherwise, and with the first build put back it fails the way the user's page did. Run it whenever the row's selectors, the marker or the tap handling change. Two facts from that page: the `mc-llm-meta` marker survives Gradio's markdown sanitizer with its `data-*` attributes and `hidden`; and stock 4.40.0's `Chatbot` takes no `autoscroll` keyword, which `mc_llm_chat_panel` passes — the user's Forge Neo builds the panel, so its Gradio is a 4.40-lineage build of its own (Forge Neo pins `fastapi==0.127.1`, `pydantic==2.10.6`). A node stub has no host; a check against it proves nothing about the host.

## Standing conventions

These recur across the handoffs and the user has restated them repeatedly.

- **Develop on the designated branch.** Commit with clear messages, push when complete. Since handoff 34 the repository's default branch is **`main`** (made at `d34d21d` when 33 was rolled back); the user's WebUI extension folder follows it, and pull requests go into it.
- **Do not open a pull request unless explicitly asked.** The user opens them from the Claude Code UI.
- **No model identifier** in commit messages, PR text, code comments, or anything else pushed to the repository.
- **Run the full suite before every push**: `python3 tools/run_tests.py`, not just the file you touched. It runs every test on every core through pytest-xdist, which `.claude/hooks/session-start.sh` installs in web sessions (about 2½ minutes on four cores, 7¼ on one; `--serial` for file order). Ordering-dependent failures exist: a test passing alone may fail in the suite, or beside another worker. While working, `python3 tools/run_tests.py --affected` runs only the test files the change can reach (`--list` says why): it follows imports, files named in strings, listed folders and the conftest fixtures a test asks for, and cannot see state one test leaves for another, so it never stands in for the full run. `tests/test_vibevoice_upstream.py` skips here: it runs the VibeVoice worker against upstream's own code (a tiny model on the CPU) and needs `torch`, `transformers` 4.51.3, `diffusers` and the `vibevoice` 0.0.1 wheel in a venv; run it with that venv's pytest (about a minute) whenever the worker's solver, attention or per-take randomness changes. `tests/test_llm_studio_live.py` skips too unless `MC_GRADIO_PYTHON` names a venv with Gradio 4.40.0, Playwright and Mini Paint NEO's pins (see the Gradio trap above); run it whenever LLM Studio's action row, its marker or its tap handling changes — the node harness alone passed a build on which no tap worked. A fresh web container lacks `httpx`, without which 135 LLM tests error at import (`prompt_master`'s downloader), and the Playwright package, without which every real-browser test skips; `.claude/hooks/session-start.sh` installs both since handoff 43, and the tests' launcher finds the container's own Chromium when Playwright's does not match it.
- **A test never writes into the checkout.** The stand-in host's data path is `.`, so a voice or LLM path a test forgot to redirect lands in `model_chain_voice/` or `model_chain_llm/` of the repository, where every later test, run and parallel worker finds it. A guard in `tests/conftest.py` fails such a test: ask for `voice_root`, or point `mc_llm_paths.data_root` at `tmp_path`.
- **Mutation-check new tests.** A test asserting a new invariant must fail when the change is reverted. Several tests in this project's history passed for the wrong reason until checked this way. A mutation that puts a Python file back within the same second at the same size (a `2` for a `3`) leaves a `.pyc` compiled from the mutant that Python takes for current — the file says one thing and the imported module another, and the full suite then fails a test that passes on the file as written. Delete the module's `__pycache__` entry after every restore (handoff 43's mutation tools do).
- **When a behaviour change invalidates a test's setup** (not its intent), translate the setup rather than deleting the test.
- **Do not edit files while pytest is running** — it invalidates the run.
- **Update `README.md`** when declared behaviour changes.
